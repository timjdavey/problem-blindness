# Clustered vs scattered runs

An axis in the [Randomness](index.md#randomness) set of the [environment](index.md#environment) group.

When runs disagree, do they fall into a few clear groups, so a few clues can tell you which one you are in, or do they scatter with no pattern to latch onto? No two snowflakes are alike, yet each is a plate, a column or a star. Climate runs for the UK split into a warm group and a cold one, where the Atlantic current fails. Tim Davey measures how tightly runs group and calls it cohesion.

## Actions

**Clustered runs**: Name the groups and plan for each.
- Sort the runs or outcomes into groups and report each one, not the pooled average. Two clear groups averaged together give a result neither produced. [4, 5]
- Pick the early signals that tell the groups apart, and update your belief about which group you are in as they come in. A few readings can rule out a whole group. [4]
- Keep a playbook for each group, so you can switch as soon as the signals point one way. [4]
- Choose the method by the case, not by its average score. Measure a few features first and learn which method wins on cases like that. If the best all-round method falls only a little short, keep it and stop. [2]
- Don't serve every group with one answer. You need as many kinds of response as there are kinds of case. In 2004 the US Army brought in one camouflage pattern for every setting, and it hid soldiers worse than other patterns in several of them. [1]

**Scattered runs**: Plan for the whole spread.
- Design to fit the range, since there is no small set of types to plan for. In 1950 not one of 4,063 US Air Force pilots was average on all ten body measurements, so cockpits were made to adjust. [1, 5]
- Don't trust a few early readings to say where you will end up. With no groups, there is nothing for early evidence to latch onto. [4]
- Shrink the spread you face where you can. Narrow the job, or split it so each part meets fewer kinds of case. [1]
- Test your plan against many possible futures and look for where it fails. Then change the plan so it fails less often, or set signs that tell you when to switch course. [3]
- When you must commit, pick the option that holds up across all the runs, as under [Risk vs Knightian uncertainty](risk-vs-knightian-uncertainty.md). A plan tuned to one best guess breaks easily when the spread is wide. [3, 5]

## Correlated with

- [Coherent vs incoherent runs](coherent-vs-incoherent-runs.md) (by definition). This axis only applies once runs disagree. In a coherent system every run draws from the same spread, so there are no groups to sort.
- [Small vs large world](small-vs-large-world.md) (logic). Clear groups let you list the ways things might turn out. Scattered runs leave outcomes nobody thought to list.
- [Plentiful vs scarce data](plentiful-vs-scarce-data.md) (logic). With clear groups a few readings can rule a whole group out, so a little data goes a long way ([Cohesion](../frameworks/2023-cohesion.md)).
- [Immediate vs delayed feedback](immediate-vs-delayed-feedback.md) (logic). Clear groups give early signs of which path you are on. Scattered runs give signs that point nowhere in particular.
- [Smooth vs rugged](smooth-vs-rugged.md) (logic). A rugged landscape with a few big peaks gives one cluster per peak, as runs stall on whichever is nearest.
- [Self-righting vs tipping](self-righting-vs-tipping.md) (logic). A tipping system has a few stable states, so its runs fall into a few clear groups.
